# Synthetic Student Data Card (Annex E)

Filled from the final run on 2026-10-06: `data/synthetic/generation_log.json`, `stats.json`, `validation_report.json`. The first, failed run is kept in `run1_generation_log.json`.

| Field | What we did |
|---|---|
| Purpose | Test data for the student-services assistant. It must exercise every personal question type: attendance lookup, exam eligibility, supplementary (summer semester) eligibility, placement eligibility and what-if, including boundary cases where a wrong comparison (`>` vs `>=`) or a wrong rule version would flip the answer. |
| Generator | OpenAI API, model `gpt-4o-mini`, temperature 0.4, JSON mode. Final run: 13 LLM calls (5 edge-case batches of 2 students + 5 batches of 5 normal students, plus 3 retries). The first run used 8 more calls and was discarded (see below). Script: `scripts/generate_students.py`, which also supports a local Ollama model (`LLM_PROVIDER=ollama`). |
| Prompts | Verbatim templates in `prompts/synthetic_data/`. The exact filled prompt sent for every batch is saved in `data/synthetic/prompts_rendered/`. |
| Schema enforcement | Ollama JSON mode, then a Pydantic v2 model (`GenBatch`) with Literal types for programme / result / exam_type and numeric bounds. After that the same `validate_data.py` checks used for judge data run on every batch, plus exact checks for each edge-case student. Every problem is sent back to the model in a correction message; up to 4 attempts per batch. |
| Thresholds | Not hard-coded in prompts: the generator reads them from `data/rule_registry.csv` (as of 2026-10-06 for current rules, 2026-05-01 for the May exam session), so edge cases stay correct if a rule changes. |
| Row counts and distributions | 35 students: B.Tech CSE 2024: 10, CSE 2023: 9, EE 2024: 8, EE 2023: 8. 6 courses (3 per programme), 105 attendance rows, 106 result rows. CGPA 5.40 to 9.60, mean 7.38. Attendance: 3 rows below 75%, 10 at 75-79.99%, 19 at 80-89.99%, 73 at 90% or more. Results: 91 PASS, 11 FAIL, 1 ABSENT, 3 DETAINED. |
| Edge cases included | S1001 attendance exactly at current minimum (32/40 = 80%); S1002 one class below (31/40); S1003 FAIL one mark below pass (39) with CGPA above cut-off (what-if case); S1004 ABSENT; S1005 DETAINED; S1006 three backlogs (1 FAIL in EE201, 2 DETAINED after the model's own correction, see below); S1007 CGPA exactly at placement cut-off (6.50); S1008 just below (6.49); S1009 failed then passed in supplementary; S1010 attendance exactly at the old minimum (75%): eligible before 2026-08-01, not after. `validate_data.py --own` reports each one as found or MISSING. |
| Validation results | Final data: 0 errors, 0 violations, 0 warnings. All 10 edge-case categories found. `evaluations/run_tool_checks.py` on this data: 12/12 expected tool results. |
| What the LLM got wrong | First run (all 10 edge cases in one call): failed all 3 attempts. It left out 18 course records, put S1009's supplementary result in a duplicate record, and gave S1005 an extra failed course so `active_backlogs` did not match. The 25 normal students passed, but a new validator rule then found 3 of them with 29/40 attendance (below the May rule) who still sat the exam. Fix: edge cases in pairs, clearer S1005/S1009 wording, the new rule, and a full rerun. Final run: S1006 first had 25/40 and 28/40 attendance with FAIL instead of DETAINED (fixed on retry 2). S1009 first had a FAIL with total at or above the pass mark, then lost its fail-then-pass structure (fixed on retry 3). The other 8 batches passed first time. |
| Fixture data (not LLM) | `data/fixtures/` holds 16 hand-built students with the same edge cases (`scripts/build_fixture_data.py`). It is only for unit/workflow tests and for teammates to work before the Ollama run; the demo and the data card use the LLM-generated set. |
| Known limitations | Both batches share the same 3 courses per programme (unrealistic). One semester of results only, and attendance is stored for the same semester-3 courses whose results are already out, while students are in semester 5/7. CGPA is not derived from grades, so it does not move when a result changes (what-if says so in `assumptions`). Every course has exactly 40 classes held. NSUT documents use "summer semester" / "make-up exam" rather than "supplementary"; the tool name keeps "supplementary". Names are synthetic. Clause numbers in the rule registry are still `TBD` until checked against the PDFs. |
| Privacy | All students are fictional; no real NSUT student data was used. IDs S9000-S9999 and course codes starting JDG are left free for judges. |
